# 수정 제안과 검증

버그·개선을 말할 때와 그것을 고친 뒤 보고할 때 이 형식을 지킨다. 목적은 둘이다.
1. 사용자가 "그래서 뭐가 문제고 고치면 뭐가 좋은데?"를 되묻지 않아도 되게 한다.
2. 제안할 때 한 말이 실제로 그렇게 됐는지 증거로 확인한다. 말만 하고 확인 안 한 것을 "됐다"고 쓰지 않는다.

## 1. 제안할 때 (승인 전)

항목마다 아래 네 칸을 채운다. 하나라도 비면 제안하지 않는다(모르는 칸은 "확인 못 함: 무엇을 해 보면 알 수 있는지"로 쓴다).

| 칸 | 쓰는 것 | 기준 |
|---|---|---|
| **지금 문제** | 정확히 어디(`파일:줄`, 화면, 명령)가 어떤 상황에서 어떻게 잘못되는지 | 직접 재현한 결과(명령·출력 원문 일부)를 붙인다. 재현 못 했으면 "추정"이라고 쓴다 |
| **고치는 방법** | 무엇을 어떻게 바꾸는지. 바꾸는 범위(파일 수, 다른 저장소·복사본 여부) | 대안이 있으면 고른 이유 한 줄 |
| **나아지는 점** | 기존과 비교해 무엇이 좋아지는지. 누가(사용자·팀·다음 세션) 무엇을 할 수 있게 되는지 | "더 안전", "더 좋음" 같은 말만 쓰지 않는다. 무엇이 막히고 무엇이 되는지로 쓴다 |
| **예상 결과** | 고친 뒤 관찰할 수 있는 결과. 이것이 2절 to-be 의 검증 항목이 된다 | 측정·실행으로 확인 가능한 문장으로 쓴다(예: "`select 1` 이 행 1개를 돌려준다", "쓰기 문장은 CLI 가 거절한다") |

- 여러 항목이면 번호를 붙이고 마지막에 "몇 번을 진행할까요?"로 묻는다. 묻지 않고 고치지 않는다.
- 확인 못 한 것은 따로 모아 적는다.

## 2. 승인받고 고친 뒤 (보고)

보고는 사용자가 요구한 결과로 시작하고, 이어서 항목마다 as-is / to-be 체크리스트를 쓴다.

```
### <항목 이름>
| | as-is (고치기 전, 실측) | to-be (고친 뒤, 실측) | 확인 |
|---|---|---|---|
| <예상 결과 1> | <고치기 전 실행 결과> | <고친 뒤 실행 결과> | ✅ / ❌ / ⚠️ 확인 못 함 |
```

- **행은 1절 "예상 결과"와 "나아지는 점"에서 나온다.** 제안 때 한 말마다 한 줄. 제안에 없던 것을 바꿨으면 그것도 한 줄 더한다.
- **as-is 도 실측이다.** 고치기 전에 같은 명령·테스트를 돌려 결과를 남겨 둔다(고친 뒤에는 되돌려 재지 못한다). 이미 고쳤으면 `git stash`·이전 커밋으로 재거나, 못 쟀다고 쓴다.
- **to-be 는 같은 방법으로 잰다.** as-is 와 같은 명령·입력으로 돌려 비교할 수 있게 한다.
- 확인 칸은 증거가 있을 때만 ✅. 테스트가 통과했다는 것만으로 동작을 확인했다고 하지 않는다. 실제로 확인한 범위를 쓴다(예: "AI 세션에서만 확인, 사람 터미널은 안 돌림" → ⚠️).
- ❌ 나 ⚠️ 가 있으면 숨기지 않고 표 아래에 이유와 다음 행동을 적는다.
- 회귀 확인(기존 테스트·빌드 결과, 통과 수)을 표 아래 한 줄로 붙인다.

## 하지 않는 것

- 문제만 말하고 고치는 방법·나아지는 점을 빼먹기.
- "고쳤습니다"로 끝내고 체크리스트 없이 보고하기.
- 제안 때 말한 효과를 실제로 재지 않고 ✅ 표시하기.
