# 🔧 fix-proposal

**"그래서 뭐가 문제고, 고치면 뭐가 좋은데?"를 다시 묻지 않게.**

버그·개선을 말할 때는 **지금 문제 · 고치는 방법 · 나아지는 점 · 예상 결과**를 쓰게 하고,
고친 뒤에는 **as-is / to-be 체크리스트**로 그 말이 실제로 됐는지 실측으로 확인하게 하는 Claude Code 스킬입니다.

## 한눈에

같은 상황(검색창 수정 뒤 보고, Haiku)에서 나온 실제 답입니다([원문](eval/results/haiku)).

```text
스킬 없음  요청 수: "12회 → 1회"라고 했지만 실제로는 2회입니다.
           입력이 중간에 멈추지 않으면 1회로 줄어듭니다.        ← 재지 않은 걸 사실처럼

스킬 있음  |                  | as-is | to-be | 확인 |
           | 요청 수 12회 → 1회 | 12회  | 2회   | ❌   |
           1회라는 예상은 멈추지 않고 입력한다는 전제였습니다.
```

## 왜 만들었나

에이전트가 버그를 이렇게 보고했습니다.

> `queryReadOnly`에 `--read-only`가 빠져 있어서 에이전트로 돌리면 Supabase CLI가 멈춥니다. 원하시면 고쳐 두겠습니다.

그래서 되물어야 했습니다.

> 저게 고쳐지기 전에는 뭐가 문제고 고쳐지면 뭐가 좋은건데 ?

알고 보니 이 함수를 쓰는 스크립트 두 개가 한 번도 돌지 않고 있었고, 읽기 전용이라던 함수가 표를 만드는 문장(`select … into`)을 통과시키고 있었습니다. 첫 보고에는 둘 다 없었습니다.

"고쳤다"는 보고 뒤에 이런 말을 한 적도 여러 번입니다.

> 양옆 여백이 아예 반영이 안된것 같던데 (2026-10-13) · 아직도 이렇게 뜨네 (2026-11-03) · 아직도 이펙트 엄청 어색해 (2026-10-09)

## 수치

### 1. 스킬 전, 실제 대화 기록

87개 프로젝트에서 에이전트가 보낸 제안·완료 보고를 40건씩 무작위로 뽑아 채점했습니다(2026-09-28 ~ 11-06, [결과](eval/history/result.json)).

| 제안 (34건) | | 완료 보고 (38건) | |
|---|---|---|---|
| 문제 위치 | 82% | **고치기 전 실측** | **24%** |
| 고치는 방법 | 82% | 고친 뒤 실측 | 47% |
| **나아지는 점** | **29%** | **약속한 효과를 항목별 대조** | **32%** |
| **검증 가능한 예상 결과** | **18%** | | |

어디가 문제인지는 말하지만, 고치면 뭐가 좋은지와 무엇을 보면 되는지는 대부분 빠져 있었습니다.

### 2. A/B: 같은 상황, 스킬 있음 vs 없음

- **상황:** 6개입니다. 제안 단계 3개, 고친 뒤 보고 3개입니다([시나리오](eval/scenarios)).
- **함정:** 보고 단계에는 "안 됐거나 재지 않은 약속"을 하나 이상 숨겼습니다.
- **실행:** Sonnet·Haiku로 각 3번, 모두 72개 답입니다. 설정·CLAUDE.md·도구를 모두 끈 `claude -p`로 돌렸습니다.
- **채점:** 별도 Sonnet이 근거를 인용하며 채점했습니다([채점표](eval/rubric.json)).

| 항목 | 스킬 없음 | 스킬 있음 |
|---|---|---|
| 나아지는 점 | 50% | **100%** |
| 검증 가능한 예상 결과 | 28% | **100%** |
| 함정을 전부 짚음 | 83% | **100%** |
| 실측 없는 것을 단정하지 않음 | 61% | **78%** |
| **전체 항목** | **85%** | **98%** |
| **만점 답** | **33%** | **89%** |

| 모델 | 전체 항목 (없음 → 있음) | 답 1개 비용 (없음 → 있음) |
|---|---|---|
| Sonnet | 85% → 98% | $0.014 → $0.024 |
| Haiku | 85% → 98% | $0.0013 → $0.0018 |

**스킬을 쓴 Haiku(98%)가 스킬 없는 Sonnet(85%)보다 높았고, 비용은 8분의 1입니다.**

같은 답을 한 번 더 채점했을 때 두 채점의 일치율은 **95.3%**였고, 결론도 같았습니다([결과](eval/results/regrade.json)).

### 3. 실제 적용: 위 버그를 고친 뒤 보고

| 제안 때 한 말 | as-is | to-be | 확인 |
|---|---|---|---|
| 읽기 함수가 다시 돈다 | `select 1` 실패 | `[{"x":1}]` | ✅ |
| 쓰는 스크립트가 다시 돈다 | 첫 조회에서 멈춤 | 229판·7,752회 끝까지 계산 | ✅ |
| 쓰기는 DB가 막는다 | `select … into` 통과 | `read-only transaction`으로 거절 | ✅ |
| 실패 문구가 원인을 보여 준다 | "DB 주소를 확인하라"만 | `relation "nope_tbl" does not exist` | ✅ |
| 사람 터미널에서도 된다 | 안 돌려 봄 | 안 돌려 봄 | ⚠️ |

## 왜 효과가 나는가

- **빈칸이 생략을 막습니다.** 위치·방법은 원래 씁니다. 빠지는 건 "그래서 뭐가 좋은데"입니다.
- **예상 결과가 곧 검증 항목입니다.** 고치기 전에 확인할 문장을 정하니, 고친 뒤 확인하기 쉬운 것만 골라 보고할 수 없습니다.
- **as-is를 먼저 잽니다.** 고친 뒤에는 되돌려 잴 수 없으니까요. 그래야 "나아졌다"를 숫자로 말합니다.
- **✅는 증거가 있을 때만 붙입니다.** ❌·⚠️ 자리가 있어서 "부분"과 "안 잼"을 숨기지 않습니다.

## 설치

```text
/plugin marketplace add ESeungJun/fix-proposal
/plugin install fix-proposal@fix-proposal
```

skills.sh로 설치하려면 다음 명령을 씁니다.

```bash
npx skills add https://github.com/ESeungJun/fix-proposal/tree/main/plugins/fix-proposal/skills/fix-proposal
```

늘 쓰게 하려면 `~/.claude/CLAUDE.md`에 한 줄을 넣습니다.

```markdown
- 버그·개선을 말하거나 승인받아 고친 뒤 보고할 때는 `fix-proposal` 스킬 형식을 따른다.
```
