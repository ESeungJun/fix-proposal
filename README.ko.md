# 🔧 fix-proposal

**"그래서 뭐가 문제고, 고치면 뭐가 좋은데?"를 다시 묻지 않게.**

에이전트가 버그·개선을 말할 때 **지금 문제 · 고치는 방법 · 나아지는 점 · 예상 결과** 네 칸을 채우게 하고,
승인받아 고친 뒤에는 **as-is / to-be 체크리스트**로 그 말이 실제로 그렇게 됐는지 실측으로 확인하게 하는 Claude Code 스킬입니다.

## 한눈에

같은 상황(검색창 디바운스 수정 뒤 보고, Haiku)에서 스킬이 없을 때와 있을 때 실제로 나온 답입니다([원문](eval/results/haiku)).

```text
┌─ 스킬 없음 ───────────────────────────────────────────────
│ 요청 수: 앞서 "12회에서 1회"라고 했지만, 실제로는 2회입니다.
│ ... 이건 정상 동작이며, 입력이 중간에 멈추지 않으면 1회로 줄어듭니다.   ← 재지 않은 것을 사실처럼 씀
└──────────────────────────────────────────────────────────
┌─ 스킬 있음 ───────────────────────────────────────────────
│ |                 | as-is | to-be                        | 확인 |
│ | 요청 수 12회 → 1회 | 12회  | 2회 (`아이폰`, `아이폰 케이스`) | ❌   |
│ 1회라는 예상은 300ms 넘게 멈추지 않고 입력한다는 전제에서 나온 값이었습니다.
└──────────────────────────────────────────────────────────
```

두 답 모두 "300ms 안에 표시"는 재지 않았다고 밝혔습니다. 갈린 곳은 위 한 줄입니다. 스킬이 없는 답은 재지 않은 "멈추지 않으면 1회"를 사실처럼 썼습니다. 스킬이 있는 답은 ❌로 두고 그 예상이 어떤 전제에서 나왔는지만 적었습니다.

## 왜 만들었나

만든 사람(Claude Code로 개인·팀 프로젝트를 개발)이 실제로 겪은 일입니다.

**2026-11-06, 데이터 스크립트 버그.** 에이전트가 작업 끝에 이렇게 보고했습니다.

> `scripts/combos/lib/match-log.mjs`의 `queryReadOnly`에 `--read-only`가 빠져 있어서, 에이전트로 돌리면 Supabase CLI가 확인을 요구하며 멈춥니다. … 원하시면 이슈를 만들고 고쳐 두겠습니다.

위치와 고칠 방법은 있었습니다. 하지만 고치지 않으면 무엇이 안 되는지, 고치면 무엇이 좋아지는지는 없었습니다. 그래서 사용자가 이렇게 되물었습니다.

> 저게 고쳐지기 전에는 뭐가 문제고 고쳐지면 뭐가 좋은건데 ?

답을 들어 보니 이 함수를 쓰는 스크립트 두 개가 AI 세션에서 **한 번도 돌아가지 않는 상태**였습니다. 게다가 읽기 전용이라고 믿었던 함수가 `select … into`(표를 만드는 문장)를 그대로 통과시키고 있었습니다. 첫 보고에서는 둘 다 빠져 있었습니다.

**"고쳤다"고 했는데 아니었던 일.** 같은 기간 대화 기록에 실제로 남은 말입니다.

> 양옆 여백이 아예 반영이 안된것 같던데 코드 제대로 확인하고 실기기에서도 테스트해줘 (2026-10-13)
>
> 아직도 이렇게 뜨네 (2026-11-03, macOS 앱 서명 경고를 고쳤다고 한 뒤)
>
> 아직도 이펙트 엄청 어색해 (2026-10-09)

이것이 한두 번의 일인지 확인하려고 지난 기록 전체를 쟀습니다(아래 1).

## 수치

### 2. A/B 실험: 같은 상황, 스킬 있음 vs 없음

- **상황:** 6개입니다([`eval/scenarios`](eval/scenarios)).
  - 제안 단계 3개: 데이터 스크립트, 웹 검색창, 안드로이드 날짜 표시
  - 보고 단계 3개: 위 셋을 고친 뒤
  - 보고 단계에는 **제안 때 한 말 중 실측으로는 안 됐거나 재지 않은 것**을 일부러 하나 이상 넣었습니다(함정).
- **조건:** 기준선은 "코딩 에이전트, 한국어로 답" 한 줄입니다. 스킬 조건은 같은 줄에 `SKILL.md` 본문을 더한 것입니다.
- **실행:** Sonnet과 Haiku로 각각 3번씩, 모두 72개 답을 받았습니다.
  - 빈 폴더에서 설정·CLAUDE.md·스킬·도구를 모두 끄고 `claude -p`로 돌렸습니다.
  - 기준선 쪽에 이 스킬이 섞이지 않은 것을 확인했습니다.
- **채점:** 별도 Sonnet이 [채점표](eval/rubric.json)대로 항목마다 답에서 근거를 인용하게 했습니다.
  - 인용한 문장이 답에 실제로 없으면 코드가 불합격으로 바꿉니다.
  - 상황마다 정답표([`key.json`](eval/key.json))에 모르는 것과 함정을 적어 두었습니다.

| 항목 (두 모델 합, 각 18회) | 스킬 없음 | 스킬 있음 |
|---|---|---|

- 두 번째 채점만 보면 스킬 없음 200/234(85%), 스킬 있음 233/234(99.6%)로 결론이 같습니다.

### 3. 실제 적용 사례: 위 데이터 스크립트 버그

스킬 형식으로 다시 제안하고, 승인받아 고친 뒤 보고한 표입니다. 고치기 전 값은 고친 코드를 `git stash`로 되돌려 같은 명령으로 쟀습니다.

| 제안 때 한 말 | as-is (실측) | to-be (실측) | 확인 |
|---|---|---|---|
| 경기 기록을 읽는 함수가 다시 돈다 | `select 1`이 실패 | `[{"x":1}]`, 실제 표 건수 조회(111)도 성공 | ✅ |
| 이 함수를 쓰는 스크립트가 다시 돈다 | 첫 조회에서 멈춤 | 229판·선택 7,752회를 끝까지 계산 | ✅ |
| 낱말 검사가 놓친 쓰기를 DB가 막는다 | `select … into`가 낱말 검사를 통과 | CLI가 `cannot execute SELECT INTO in a read-only transaction`으로 거절 | ✅ |
| 실패 문구가 원인을 가리지 않는다 | 무엇이 틀려도 "DB 주소를 확인하라"만 나옴 | `relation "nope_tbl" does not exist`처럼 원인이 나옴(연결 문자열은 지움) | ✅ |
| 사람이 터미널에서 돌려도 된다 | 안 돌려 봄 | 안 돌려 봄 | ⚠️ 확인 못 함 |

회귀: 테스트 274/274 통과. 마지막 줄처럼 재지 않은 것은 ✅로 바꾸지 않고 그대로 남깁니다.

## 왜 효과가 나는가

수치에서 보이는 것을 원인별로 묶었습니다.

1. **빈칸이 생략을 막습니다.** 에이전트는 위치·방법은 원래 잘 씁니다(감사 82%). 빠지는 것은 "그래서 뭐가 좋은데"입니다. 네 칸을 정해 두니 나아지는 점은 50%에서 100%, 예상 결과는 28%에서 100%가 됐습니다.
2. **예상 결과가 그대로 검증 항목이 됩니다.** 제안 때 "`select 1`이 행 1개를 돌려준다"처럼 실행해서 확인할 수 있게 쓰게 합니다. 이 문장이 나중에 to-be 표의 한 줄이 됩니다. 무엇을 확인할지가 고치기 전에 정해지니, 고친 뒤 확인하기 쉬운 것만 골라 보고하는 일이 줄어듭니다.
3. **as-is를 먼저 잽니다.** 고친 뒤에는 되돌려 잴 수 없으니 고치기 전에 재게 합니다. 그래야 "나아졌다"를 숫자로 말할 수 있습니다. 감사에서 고치기 전을 실측으로 적은 보고는 24%였습니다.
4. **✅는 증거가 있을 때만 붙입니다.** 확인 칸을 셋(✅·❌·⚠️)으로 나누니 "부분적으로 됐다"와 "안 쟀다"를 쓸 자리가 생깁니다. 함정 적발이 83%에서 100%가 됐습니다.
5. **작은 모델에서 효과가 더 큽니다.** Haiku는 문제 위치를 짚는 것(7/9 → 9/9)과 함정 적발(7/9 → 9/9)까지 올랐습니다. 형식이 판단을 대신 받쳐 주기 때문입니다.

## 한계

- **스킬을 강제로 넣은 상태에서 잰 값입니다.** 실제 사용에서 Claude가 이 스킬을 스스로 불러오는 비율은 재지 않았습니다. 늘 쓰게 하려면 `CLAUDE.md`에 한 줄을 넣기를 권합니다(아래 설치).
- **표본이 작습니다.** 상황 6개 × 3회 × 모델 2개이고, 상황은 만든 사람이 썼습니다. 보고 글만 평가했고, 실제로 코드를 고치는 전 과정을 평가하지는 않았습니다.
- **채점자도 모델입니다.** 두 번 채점한 일치율은 95.3%입니다.
- **스킬을 써도 단정하는 버릇이 남습니다.** "실측이 없는 것을 단정하지 않음"은 14/18입니다. 떨어진 4건은 모두 같은 상황(V2)입니다.
  - 기록에 없는 고치기 전 상태를 표에 적은 경우: "취소 없음 (12회 모두 진행)"
  - 재지 않은 항목에 결론을 내린 경우: "구조상 이 항목은 제안이 틀렸습니다"
- **길어지고 비싸집니다.** 글은 25~54% 길어지고, 답 1개 비용은 Sonnet 기준 $0.014에서 $0.024가 됩니다.
- **한국어만 확인했습니다.** 스킬 본문과 감사 정규식이 한국어입니다. 영어 대화에서의 효과는 재지 않았습니다.

## 설치

**Claude Code 플러그인**

```text
/plugin marketplace add ESeungJun/fix-proposal
/plugin install fix-proposal@fix-proposal
```

**스킬을 읽는 다른 에이전트** ([skills.sh](https://skills.sh))

```bash
npx skills add https://github.com/ESeungJun/fix-proposal/tree/main/plugins/fix-proposal/skills/fix-proposal
```

**직접 복사**

```bash
mkdir -p ~/.claude/skills/fix-proposal
curl -fsSL https://raw.githubusercontent.com/ESeungJun/fix-proposal/main/plugins/fix-proposal/skills/fix-proposal/SKILL.md -o ~/.claude/skills/fix-proposal/SKILL.md
```

**늘 쓰게 하려면** (권장) `~/.claude/CLAUDE.md`에 한 줄 넣습니다.

```markdown
- 버그·개선을 말하거나 승인받아 고친 뒤 보고할 때는 `fix-proposal` 스킬 형식을 따른다(제안: 지금 문제·고치는 방법·나아지는 점·예상 결과 / 고친 뒤: as-is·to-be 체크리스트로 실측 검증).
```

## 다시 재 보기

`claude` CLI에 로그인되어 있어야 합니다. 쓰는 요금제에서 차감됩니다. Node.js 20 이상이 필요합니다.

```bash
node eval/run.mjs                 # A/B 72건 (이미 있는 결과는 건너뜀. 새로 재려면 eval/results/<모델> 을 지운다)
node eval/aggregate.mjs           # 항목별 표, 함정 적발, 비용
node eval/regrade.mjs             # 채점 일치율
node eval/history/audit.mjs       # 내 대화 기록(~/.claude/projects) 감사. 원문은 저장하지 않고 집계만 출력
```
